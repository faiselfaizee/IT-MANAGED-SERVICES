# ISO/IEC 27001:2022 and penetration testing

## What "meeting ISO 27001" means for this product
ISO 27001 certifies an organisation's information security management system (ISMS), not a piece of software. DamazeTech can be certified for how it develops, hosts and supports DeskAsk; customers can then rely on it. The platform's part is to provide the technical controls and the evidence an auditor asks for. The table maps the Annex A 2022 controls the platform touches to what exists today and what is missing. "Process" means a policy or routine the company must run; code cannot supply it.

| Annex A | Control | In the platform today | Gap and next step |
|---|---|---|---|
| 5.15, 5.18 | Access control, access rights | Roles (admin, engineer, viewer, customer admin), customer scope filtered in SQL, access delegation | Quarterly access review report (list of users, roles, last sign-in) |
| 5.17, 8.5 | Authentication | Hashed passwords, 10+ characters, lockout, optional two-step, Microsoft/Google/AD sign-in, PKCE | Enforce two-step for admins and engineers by default; add password breach/denylist check |
| 5.23 | Cloud services | SaaS hosting design, per-customer database | Supplier register and review (hosting, Razorpay, mail) |
| 5.24-5.28 | Incident management | Audit log, monitoring alerts | Incident process, contact list, evidence handling |
| 5.30, 8.13, 8.14 | Continuity, backup, redundancy | Backup module for customers' own backups | Back up the platform's own databases and data-protection keys; test a restore twice a year; document RPO/RTO |
| 5.34 | Privacy / personal data (DPDP Act 2023) | Customer data per tenant | Privacy notice, retention and deletion routine, breach notification steps |
| 5.36, 5.37 | Policies, documented operations | Install, update and troubleshooting docs | Information security policy and procedures signed off by management |
| 6.x | People | n/a | Screening, confidentiality agreements, awareness training, leaver process |
| 7.x | Physical | n/a (server room / hosting provider) | Physical access controls and a visitor log for the server room |
| 8.2, 8.18 | Privileged access | Vendor console limited to the vendor customer; updates limited to the vendor on SaaS (6.5.1) | Separate admin accounts, record privileged sessions |
| 8.7 | Malware protection | Signed updates, signed agent bundles | Endpoint protection on the servers |
| 8.8 | Technical vulnerabilities | CI fails on vulnerable NuGet or high/critical npm packages | Add Go vulnerability scanning (govulncheck) and a monthly patching routine with a log |
| 8.9 | Configuration management | Installer, config file with backups | Hardening baseline for IIS/Windows/PostgreSQL, checked each release |
| 8.12 | Data leakage prevention | Vault encrypted in the browser, secrets sealed | Classify data; restrict exports by role |
| 8.15, 8.16 | Logging, monitoring | Audit log of changes; Monitoring | Forward logs to a central store, keep 12 months, protect against edits, alert on repeated failed sign-ins |
| 8.20-8.23 | Network security | Per-address rate limits, SSRF protection, security headers | OPNsense: remove the allow-all rule, limit ports to 443/80 and RustDesk; TLS 1.2+ only |
| 8.24 | Cryptography | TLS (HAProxy/IIS), data protection keys, ES256 licences | Written key management: where keys live, rotation, backup |
| 8.25-8.29 | Secure development and testing | CI builds and tests every change, tests that every API route has an authorization rule | Threat model per module, code review rule for security-sensitive changes, DAST in CI |
| 8.31 | Separate dev, test, production | Dev server 10.10.100.101, planned production 10.10.10.101 | Never use production data in dev; keep `Licensing:AllowUnlicensed` off outside dev |

Suggested order: (1) network rules and two-step for staff, (2) platform backups and a restore test, (3) central logs with retention, (4) policies and risk register, (5) a penetration test, (6) internal audit, then the certification audit. A first certificate typically needs 3 to 6 months of the ISMS running with records.

## Penetration test
A real test needs a running installation to attack, which this chat session cannot reach. The earlier review (docs: security assessment of 2026-11-17) was by code and CI only. Plan for a proper test:

**Scope.** Platform web and API (`platform.deskask.in` and one test customer), customer and vendor consoles, agent and controller enrolment and relay, installer, update path, the website link and store (Razorpay webhook, signed requests), vault, RustDesk exposure.

**Environment.** A staging copy with test data and two test customers (to test isolation). Never test against paying customers.

**Checks.**
- Authentication: brute force and spraying limits, 2-step bypass, token reuse, session fixation, password reset.
- Authorisation: horizontal (customer A reads customer B by changing ids), vertical (viewer or customer calls admin and vendor routes), tenant isolation by host header.
- Injection: SQL, command (ping, SSH discovery, remote commands), template, header; file upload and path traversal (updates, attachments, installer).
- SSRF and outbound calls (web hooks, activation URL, controller relay).
- Business logic: store and licence (price tampering, replaying a payment, forging a licence or website signature), the product switch.
- Agents: enrolment tokens, key theft, relay command abuse, update signing.
- Transport and headers: TLS configuration, cookies, CSP.
- Secrets: logs, error messages, backups, configuration files.

**Method and tools.** OWASP ASVS level 2 as the checklist; OWASP ZAP and Burp Suite for web and API (authenticated scans with a test user per role); nmap and testssl.sh for network and TLS; dependency audits (npm audit, dotnet list package --vulnerable, govulncheck). An independent tester (not the developers) for the certification evidence.

**Output.** Findings with severity (CVSS), proof, fix and a re-test; keep the report as ISO evidence (A.8.8, A.8.29).
